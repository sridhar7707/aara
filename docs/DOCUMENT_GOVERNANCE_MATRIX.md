**Headline findings:**

1. **Two documentation eras coexist with almost no cross-links.** 16 root-level `docs/*.md` files (branded "TradeGenius AI", June–July 2026) describe the legacy single-bot/single-dashboard system. A much larger AARA/Sentinel-era tree (`docs/architecture/`, `docs/platform/`, `docs/products/`, `docs/decisions/`, `docs/design/`, `docs/implementation/`, `docs/analysis/` — 117 files, July–Aug 2026) describes the multi-product platform. Neither tree references the other.
2. **`docs/ARCHITECTURE.md` (root) collides by name with the `docs/architecture/` folder**, and `docs/DESIGN_SYSTEM.md` (root, legacy Gradio tokens) topically collides with `docs/architecture/SENTINEL_DESIGN_SYSTEM_FINAL.md` (new platform design system).
3. **The `docs/architecture/` folder's own authority registries disagree with each other.** `ARCHITECTURE_FREEZE_STATUS.md` lists 25 frozen documents; `ARCHITECTURE_INDEX.md` lists a different 20 "active" documents and, within itself, cites `PHASE_2_UI_UX_REQUIREMENTS_FORMAL.md` as authoritative in one section while listing the plain (non-FORMAL, stale) version as "active" in another.
4. **A genuine 3-way overlap** exists between `SENTINEL_PRODUCT_REQUIREMENTS_DOCUMENT.md` (vision/principles), `PRODUCT_SPECIFICATION_DETAILED.md` (personas/workflows), and `SENTINEL_UXRD_COMPREHENSIVE.md` (screen-by-screen UI mapping) — an undocumented but plausible PRD→spec→UXRD layering that should be made explicit or merged.
5. **The Sentinel Engine vision-tier docs in `docs/platform/` substantially duplicate each other.** `SENTINEL_ENGINE_SERVICE_ARCHITECTURE.md` and `SENTINEL_INTELLIGENCE_ENGINE_ARCHITECTURE.md` are ~80% the same document written independently; the runtime-lifecycle content appears a third time in `SENTINEL_ENGINE_RUNTIME_FLOW.md`.
6. **13 of 31 `docs/platform/` files and 11 of 15 `docs/products/` files are not individually adjudicated** in `AARA_ARCHITECTURE_AUTHORITY.md`'s "current document roles" table, despite that table being the platform's stated authority mechanism.
7. **`ADR-007` (AARA Platform Hierarchy) is still status "Proposed", not "Accepted"** — it cannot yet be cited as settled governance, even though its content (nested nesting hierarchy) is not actually in conflict with `AARA_ARCHITECTURE_AUTHORITY.md`/`AARA_PLATFORM_ARCHITECTURE.md` as currently written. **This differs from prior working assumptions that a flat-vs-nested diagram conflict was unresolved — worth a manual recheck, since the ADR-007 text may have been edited since that was last true.**
8. **`AARA_TRADING_INTELLIGENCE_MVP_SCOPE_DECISION.md` functions exactly like an ADR** (binding, cites prior analysis, makes one final call) but lives in `docs/products/` instead of `docs/decisions/`.
9. **`docs/product/CONFIDENCE_EXPLANATION_UX.md`** sits alone in a singular-named folder while everything else uses plural `docs/products/` — almost certainly a misplaced file; the document itself flags the inconsistency.
10. **`AARA_WEALTH_INTELLIGENCE_PRODUCT_ARCHITECTURE.md`** describes an aspirational product (Plaid aggregation, Wealth X-Ray/Map) with **zero matching code** — the shipped `applications/wealth_intelligence/` app is a narrow Decision-Center clone, not any of the five described capabilities.
11. **`docs/specs/SPEC_01`–`SPEC_09`** (11 files, June 2026) are fully-implemented, one-time feature build logs now redundant with the auto-generated `docs/REQUIREMENTS.md` — the cleanest archive candidate in the whole tree.

## Document Authority Hierarchy

This is the **intended** hierarchy, synthesized from `docs/platform/AARA_ARCHITECTURE_AUTHORITY.md`'s stated rule plus `docs/architecture/ARCHITECTURE_INDEX.md`'s 4-level model. It does not fully match current practice (see Consolidation Opportunities) but is the target state to converge on.

1. **Committed code** — the real, tested implementation always wins over any doc when they disagree.
2. **ADRs** (`docs/decisions/ADR-001` … `ADR-008`) — binding architectural decisions. Only ADRs with status **Accepted** are authoritative; `ADR-007` is currently **Proposed** and should not yet be treated as binding.
3. **Frozen Architecture Documents** (`docs/architecture/ARCHITECTURE_FREEZE_STATUS.md`'s 25-document list, plus `docs/platform/PHASE_0_ARCHITECTURE_VALIDATION_REPORT.md`) — within this tier, `docs/architecture/ARCHITECTURE_INDEX.md`'s 4-level sub-hierarchy applies:
   - Level 1 — Domain & Behavior: `DECISION_INTELLIGENCE_ARCHITECTURE.md` → `TRADING_CONSTITUTION.md`
   - Level 2 — Data & Events: `SYSTEM_EVENT_MODEL_v1.2.md` → `SQLITE_LEDGER_SCHEMA_v1.2.md` → `DERIVED_STATE_VIEWS_v1.2.md`
   - Level 3 — Interface Contracts: `API_REQUIREMENTS_v1.0.md` → `PHASE_2_UI_UX_REQUIREMENTS_FORMAL.md`
   - Level 4 — Implementation Guidance: `IMPLEMENTATION_HANDOFF.md` → `GRADIO_IMPLEMENTATION_GUIDE.md`
4. **Product Requirements Documents** — `SENTINEL_PRODUCT_REQUIREMENTS_DOCUMENT.md`, `AARA_TRADING_INTELLIGENCE_PRODUCT_ARCHITECTURE.md`, `AARA_WEALTH_INTELLIGENCE_PRODUCT_ARCHITECTURE.md` (the last one flagged stale vs. shipped code), and any doc functioning as one regardless of folder (e.g. `AARA_TRADING_INTELLIGENCE_MVP_SCOPE_DECISION.md`, which should be relocated to tier 2).
5. **Implementation Plans** — `docs/implementation/*`, `docs/platform/*IMPLEMENTATION_PLAN.md`, `docs/products/*_UI_IMPLEMENTATION_PLAN.md`. Non-authoritative for decisions; authoritative for sequencing only.
6. **Design Specifications** — `docs/design/`, `docs/products/*_DESIGN.md`, `docs/architecture/SENTINEL_DESIGN_SYSTEM_FINAL.md`, `docs/architecture/SENTINEL_COMPONENT_CATALOG.md`.
7. **Analysis Documents** — `docs/analysis/*`, and architecture-folder analysis docs (`RISK_GOVERNOR_SAFETY_AUDIT.md`, `CONFIDENCE_EDGE_CASE_ANALYSIS.md`, etc.). Informational; feed decisions but don't make them.
8. **Historical / Archived Documents** — `docs/specs/*`, completed roadmaps, superseded meta-audits, AI-agent working-plan artifacts (`docs/superpowers/plans/*`).

**Known gaps in applying this hierarchy today:** `docs/architecture/ARCHITECTURE_FREEZE_STATUS.md` and `docs/architecture/ARCHITECTURE_INDEX.md` disagree on tier-3 membership (see Executive Summary #3); `AARA_ARCHITECTURE_AUTHORITY.md` does not individually rule on most `docs/platform/` and `docs/products/` files, leaving their tier assignment implicit.

## Rules Going Forward

**When to create a new document:**
- A new architectural decision that binds future work → new ADR in `docs/decisions/`, not a new architecture doc.
- A new product capability or screen design → new file under `docs/products/<product>/`, named for the capability, not for the meeting/date it was written.
- A new analysis or investigation whose findings inform a future decision → `docs/analysis/`, explicitly labeled "informational, not authoritative."

**When to update an existing document instead:**
- If a document with the same topic already exists in a higher or equal authority tier (see hierarchy above), update it in place rather than writing a new "FINAL," "FORMAL," "v2," or "COMPREHENSIVE" sibling. This repo's history shows that pattern (`PHASE_2_UI_UX_REQUIREMENTS.md` → `_FORMAL.md`, `SENTINEL_ENGINE_SERVICE_ARCHITECTURE.md` vs `SENTINEL_INTELLIGENCE_ENGINE_ARCHITECTURE.md`) reliably produces undetected duplicates.
- Any doc whose claims are contradicted by shipped code (e.g. "no code exists yet") must be corrected in place before it's cited again — several docs in this matrix were caught making now-false claims.

**How frozen documents are protected:**
- A document is only FROZEN if it appears in `docs/architecture/ARCHITECTURE_FREEZE_STATUS.md`'s registry (or an equivalent single registry, once `ARCHITECTURE_INDEX.md` is reconciled with it). Frozen documents may only change via an explicit addendum (see `PHASE_2A_ARCHITECTURE_FREEZE_ADDENDUM.md` as the model) or a new ADR narrowly reopening them (see `ADR-006` as the model) — never a silent edit.
- Every FROZEN or ACTIVE-authoritative document should be listed by name in `docs/platform/AARA_ARCHITECTURE_AUTHORITY.md`'s document-roles table. This matrix found dozens of documents that are structurally binding by that doc's own rule but never individually named there — closing that gap is the single highest-leverage governance fix available.

**How superseded documents are archived:**
- Move (don't delete) to `docs/archive/`, preserving the original relative path under `archive/`, so links inside other docs still resolve to a findable location.
- Add a one-line banner at the top of the archived file: `> Archived YYYY-MM-DD. Superseded by: <path>.` — none of the files in this matrix currently carry that banner, which is why supersession had to be inferred rather than read directly in most cases.
- Do not archive a document that is still the only writer/reader-cited source for a live code path (e.g. `TRADING_INTELLIGENCE_SENTINEL_LEDGER_INTEGRATION_OPTIONS.md`, which ADR-004 references) — archive only once a successor exists and is confirmed to cover the same ground.
