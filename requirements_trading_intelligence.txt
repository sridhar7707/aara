# HuggingFace Spaces runtime dependencies for AARA Trading Intelligence
# (applications/trading_intelligence/) — kept minimal, no ML/trading packages.
#
# gradio==4.44.1, not dashboard/'s 5.9.0 (requirements_space.txt):
# PyPI metadata confirms gradio 5.9.0 requires Python >=3.10, while 4.44.1
# supports Python >=3.8. applications/trading_intelligence/'s test suite
# (272 tests) and its Decision Center UI's documented Gradio-4.44.1-specific
# keyboard-selection behavior (see gradio_view.py's own module docstring,
# "Gradio 4.44.1's Dataframe keyboard gap") have only ever been run against
# this exact version — 5.9.0 compatibility is unverified. Do not upgrade
# this pin without re-verifying that behavior against the new version.
gradio==4.44.1
pillow>=10.4.0

# gradio==4.44.1 declares only huggingface-hub>=0.19.3 (no upper bound), so
# an unpinned install picks up the latest huggingface_hub -- which removed
# HfFolder starting at 1.0.0 (verified against GitHub source at each tag:
# present through v0.36.2, gone at v1.0.0 and every release since). gradio
# 4.44.1 imports HfFolder internally (gradio/oauth.py) and crashes on start
# without it -- confirmed via the actual HF Space runtime traceback
# (ImportError: cannot import name 'HfFolder' from 'huggingface_hub').
# 0.36.2 is the narrowest pin: the exact last release that still has it.
huggingface_hub==0.36.2

# gradio==4.44.1 declares no direct starlette pin; it depends on fastapi<1.0,
# and unpinned fastapi (0.141.1) pulls starlette>=0.46.0's latest -- 1.6.0,
# which dropped the deprecated TemplateResponse(name, context_dict) calling
# convention gradio/routes.py:432 uses (starlette>=1.0.0 keeps only the new
# TemplateResponse(request, name, context) signature). Confirmed directly
# against starlette source: 0.52.1's TemplateResponse still special-cases
# `isinstance(args[0], str)` to correctly unpack the old-style (name, dict)
# call gradio makes; that branch is gone starting at 1.0.0, which is why
# jinja2 ends up handed a dict as the template name (TypeError: unhashable
# type: 'dict') -- confirmed via the actual HF Space runtime traceback.
# 0.52.1 is the latest starlette release still containing that shim.
starlette==0.52.1

# ADR-028 Section 2.3: exactly one Supabase Python SDK package, the narrow
# supabase-auth client (not the full "supabase" package, which additionally
# pulls in realtime/storage/functions/postgrest this adapter never uses).
# Verified via a clean pip dependency-resolution dry-run against this exact
# file (--ignore-installed --python-version 3.9 --only-binary=:all:): resolves
# cleanly alongside gradio==4.44.1/huggingface_hub==0.36.2 with no version
# conflict -- httpx resolves to 0.28.1 (satisfies both gradio's >=0.24.1 and
# supabase-auth's <0.29,>=0.26) and pydantic resolves to 2.13.4 (satisfies
# both gradio's >=2.0 and supabase-auth's <3,>=1.10). Not verified against
# this file's pre-existing starlette==0.52.1 pin, which independently fails
# to resolve under Python 3.9 (requires >=3.10) -- a pre-existing issue
# unrelated to this addition, not introduced or fixed by it.
supabase-auth==2.31.0

# zoneinfo (stdlib since Python 3.8) needs an IANA time zone database to
# resolve "America/Chicago" -- Decision Center's timestamps are converted
# to it for display (ui/decision_center/screen.py's
# format_display_timestamp(), P1 UI-only timestamp fix). Not guaranteed
# present on this minimal HF Space image (unlike a full OS install, which
# usually ships /usr/share/zoneinfo); tzdata is the official CPython
# fallback package providing that data cross-platform, so this doesn't
# depend on the deploy image happening to include system tzdata.
tzdata

# HF ZeroGPU runtime requirement (see main.py's _zero_gpu_startup_probe) --
# this Space's hardware (zero-a10g) refuses to start without at least one
# @spaces.GPU-decorated function present. Deliberately unpinned: HF's own
# ZeroGPU Docker build template appends its own explicit `spaces==X.Y.Z`
# (matching whatever it currently ships, e.g. 0.51.1) to the same pip
# install command line that also runs `-r requirements.txt` -- a hard `==`
# pin here that doesn't match exactly causes a direct, unresolvable pip
# conflict (both are explicit user requests for the same package) and
# fails the Space build outright (confirmed via the actual build log,
# 2026-08-16: "Cannot install spaces==0.46.0 and spaces==0.51.1"). The
# @spaces.GPU decorator's API has been stable across these versions, so
# there's nothing this pin was protecting beyond a resolver dry-run.
spaces

# alpaca-py: the two read-only Alpaca adapters in this product --
# adapters/alpaca_paper_source.py (paper account + positions) and
# adapters/alpaca_news_source.py (Overnight Holdings News). Both are
# GET-only observation: no order/execution API is imported or reachable.
# Without this package installed, each adapter's lazy `import alpaca...`
# raises inside a try/except and the adapter returns None, so the app
# still starts and the affected sections stay on their existing honest
# unavailable state -- adding it here is what lets those sections show
# real data in the deployed Space (which also needs ALPACA_KEY /
# ALPACA_SECRET provided as Space secrets). Same lower-bound pin as the
# root requirements.txt (`alpaca-py>=0.40.0`); local dev already has it
# from that file. This is the one non-minimal dependency in this list --
# it pulls pandas/numpy transitively -- and is justified by the two
# adapters above being the only path to real broker data in the Space.
alpaca-py>=0.40.0

# ADR-063: python-dotenv -- required because the staged top-level config.py
# (ADR-056 Section 2.1) begins with an unguarded `from dotenv import
# load_dotenv`. Not pulled transitively by anything else in this file
# (gradio 4.44.1, gradio-client 1.3.0, plain uvicorn, starlette, spaces,
# alpaca-py, supabase-auth, pillow, tzdata all checked -- none declare it),
# so on the minimal HF Space image `import config` raises
# ModuleNotFoundError and every `from config import ...` across the product
# (the three read-only Alpaca adapters and adapters/trades_db_snapshot.py)
# silently falls back to empty values -- confirmed via the deployed Space's
# rendered NOT_CONFIGURED state despite ALPACA_KEY/ALPACA_SECRET being
# synced as Space secrets (ADR-060). Pure-Python, zero-dependency; in the
# Space there is no .env file so load_dotenv() is a no-op and values still
# come from os.getenv() reading the Space secret store. ADR-062 Section 3
# item 5 deferred this pending runtime evidence; that evidence now exists.
python-dotenv

# yfinance -- adapters/live_price_source.py's live current-price fetch,
# which composes with LegacyPositionSource to give Portfolio Intelligence's
# Holdings table real market value and weights. Not pulled transitively by
# anything else in this file (gradio 4.44.1, gradio-client 1.3.0, plain
# uvicorn, starlette, spaces, alpaca-py, supabase-auth, pillow, tzdata,
# python-dotenv all checked -- none declare it), so on the minimal HF Space
# image `import yfinance` raises and the adapter reports NOT_CONFIGURED
# ("yfinance not importable") -- confirmed via the deployed Space's rendered
# "Holdings data is currently unavailable" state. Same isolated live-network
# dependency the adapter's own docstring already records as authorized;
# duplicates dashboard/'s yfinance.download() primitive rather than importing
# the protected package. Unpinned, matching the root requirements.txt.
yfinance
